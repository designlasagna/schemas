# RFC 0003: v0.5 candidates — what still needs a breaking version

> **Status:** Proposed — awaiting Magnus's decisions D1–D6 below. Nothing here is implemented in the schemas.
> **Authors:** AI-assisted draft for Magnus review
> **Created:** 2026-10-14
> **Target version:** none yet (see Recommendation)
> **Related:** schemas review 2026-10-07 (vault), [Open schemas, warning tools](../docs/openness.md), decisions [0001](../docs/decisions/0001-remove-platform-mapping-usage.md) and [0002](../docs/decisions/0002-keep-platform-mapping-closed.md), `docs/dtcg-mapping.md`

## Summary

The October 7 schemas review left a list of changes that would reject documents valid under v0.4, so each needed a new version directory: v0.5. That list was written before the open-schemas policy of 2026-10-14. Re-read against the policy, most of it changes shape:

| # | Item | Was | Recommended now | Needs v0.5? |
|---|---|---|---|---|
| 3 | `removal` format | schema rejects malformed values | tools warn | no |
| 4 | `metadata.extensions` reservation | schema rejects authored key | token-core warns now; schema rule only if v0.5 is cut for other reasons | not by itself |
| 5 | structured layered values | open question | additive optional field when a native emitter needs it | no |
| 6 | shared `common.json` | v0.5 | only alongside another breaking change | not by itself |
| 8 | vendor prefix for CEM lifecycle fields | v0.5 | keep unprefixed; revisit if CEM claims the names | no |
| 9 | relative `docs.url` | undecided | keep absolute | no |

Items 7 and the rest of 9 were settled on 2026-10-14 (intentional strictness difference; tool warnings).

**Recommendation: do not cut v0.5 now.** Nothing on the list fixes a problem a real consumer has today, and every breaking change makes every producer migrate. Keep a v0.5 backlog (below) and cut v0.5 when a breaking change is needed for a concrete reason; the backlog items ride along then.

Two things make this possible:

- **Tool warnings replace schema rejections.** The language server work tracked as `task-2026-10-14-manifest-field-warnings` covers unknown fields, malformed `removal` values, undeclared variant kinds and suspicious empty values.
- **Additions are not breaking.** A new optional field or a newly accepted value only relaxes validation, so it fits a 0.4.x patch under the hosted URL policy. Several "v0.5" ideas are additions.

---

## Item 3 — `removal` format

**Today.** `removal` is any string. The descriptions name three forms (ISO date, SemVer, `YYYY-Qn`) and the language server treats only real dates as time-aware.

**Earlier decision (2026-10-09).** Magnus approved four formats — calendar dates, SemVer, `YYYY-Qn`, legacy `Qn-YYYY` — and that schema validation would reject everything else in a future contract. That predates the open-schemas policy.

**Options.**

- **3a — Schema rejects** (the 2026-10-09 plan). A pattern per form plus `format: date`. Costs: free text such as `"next major"` or `"after the redesign"` becomes invalid, which forces a format on design systems that plan removals differently. Date validity depends on the validator enabling format assertions; without them a pattern only checks shape.
- **3b — Tools warn** (recommended). The schema keeps accepting any string and its descriptions list the recognised forms. The language server warns: "`removal` isn't a recognised date, version or quarter; time-based severity won't apply." Authors learn about the mistake where it matters, and nobody is forced.

**Why 3b.** A malformed `removal` is exactly the policy's "valid but probably a mistake" case. The cost of the mistake is that time-based severity doesn't apply, which a warning explains better than a schema error.

**D1.** Choose 3b and retire the 2026-10-09 schema plan — or keep 3a for v0.5.

## Item 4 — `metadata.extensions` reservation

**Today.** token-core copies every foreign `$extensions` key into manifest `metadata.extensions`. If an author also writes `$extensions["recipes.designlasagna"].metadata.extensions`, the generated value overwrites theirs **silently**. A test-only draft schema (`test/fixtures/FUTURE-dtcg-metadata-reservation.schema.json`) rejects the authored key; Magnus approved that collision policy, but no contract version activates it.

**Under the policy** this is our own authoring namespace, so a schema rule is allowed. But the actual harm today is silent data loss, which a schema version change does not fix for anyone still on v0.4.

**Options.**

- **4a — Activate the schema rule in v0.5.** Correct but slow: only helps once producers move to v0.5.
- **4b — token-core warns now** (recommended, in addition to 4a later). When an authored `metadata.extensions` is present, warn that it will be replaced by generated foreign extensions and suggest a sibling key. Non-breaking; works on v0.4 today.

**D2.** Approve 4b now, and keep the 4a schema rule in the v0.5 backlog.

## Item 5 — structured layered values

**Today (since 0.4.4).** Multi-layer shadows and gradients resolve to an array of strings, one per layer, CSS-like: `"inset 0px 8px 4px 0px #000000"`. That fixed the `"[object Object]"` bug.

**The open question.** `docs/boundaries.md` says the manifest must be sufficient: anything downstream can produce any output from it alone. A Swift or Compose emitter would have to parse a CSS-like string to build a native shadow. `modes` keeps the authored structure but may contain aliases, so it is not a substitute.

**Options.**

- **5a — Keep strings only.** Fine for web consumers and the language server; native emitters parse strings.
- **5b — Also accept arrays of objects in `resolved`.** A relaxation, but consumers that assume strings would break on producers that switch, and the same token could appear in two shapes.
- **5c — Add an optional structured field** (recommended, when needed). Keep `resolved` render-ready; add an optional per-condition field — working name `resolvedStructured` — carrying the alias-free DTCG-shaped value (`[{ color, offsetX, offsetY, blur, spread, inset }]`, `[{ color, position }]`). Additive, so a 0.4.x patch can carry it; consumers that don't know it ignore it.

**Why 5c, and why not yet.** It keeps one shape per field and needs no new version. No native emitter exists yet, so there is no consumer to design it against; adding it speculatively risks the wrong shape.

**D3.** Agree 5a now and 5c when a native emitter needs it (no v0.5).

## Item 6 — shared `common.json`

`DesignSystemMeta` and `Docs` are copied into tokens, utilities and icons. A shared `common.json` would remove the copies, but every consumer that registers schemas by hand (token-core, the website, any third party) must register one more file, and the website must host it. 0.4.5 already removed the copies that could be removed within one file.

**D4.** Do it only when v0.5 is cut for another reason (backlog).

## Item 8 — vendor prefix for CEM lifecycle fields

**Today.** `status`, `removal` and `replacement` sit directly on CEM entries next to the standard `deprecated`. The pinned CEM schema defines none of the three, so there is no clash today.

**Options.**

- **8a — Keep unprefixed** (recommended). Document the three names as Design Lasagna vendor fields and watch the CEM spec. If CEM ever proposes one of them, decide then — with a real definition to align with or avoid.
- **8b — Prefix in v0.5** (for example `dlStatus`, or nesting under a vendor key). Breaks every CEM producer and analyzer plugin and the language server, to avoid a clash that may never happen.

**D5.** Choose 8a.

## Item 9 — relative `docs.url`

`docs.url` (and `figma`, `storybook`) must be absolute URIs. Accepting relative links would be a relaxation, but a relative link means nothing in an editor hover unless the consumer resolves it against `designSystem.documentation`, and no consumer does.

**D6.** Keep absolute-only. If relative links are wanted later, define the resolution rule first; accepting them is then a 0.4.x relaxation, not v0.5.

## v0.5 backlog

Breaking changes to collect until v0.5 is cut for a concrete reason:

- Activate the `metadata.extensions` reservation in the DTCG namespace (item 4a), if D2 keeps it.
- Shared `common.json` (item 6), if D4.
- `removal` format rejection (item 3a), only if D1 keeps it.

Anything added here needs a decision record in `docs/decisions/` when it ships (see `docs/openness.md`).
