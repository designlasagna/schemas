# RFC 0001: Schema v0.3 — Generalization & Missing Capabilities

> **Status:** Draft  
> **Authors:** Magnus Fredlundh  
> **Created:** 2026-05-19  
> **Target version:** 0.3.0  

## Summary

This RFC proposes changes to the Design Lasagna schemas to make them more universally adoptable by any design system, regardless of organizational model, platform focus, or lifecycle terminology. It also adds capabilities that are missing for real-world multi-platform, multi-brand, and multi-condition design systems.

## Motivation

The v0.2 schemas work well but encode assumptions that reflect one specific system's structure:

1. **Forced hierarchical token organization** — not all systems use group/category
2. **Forced utility categorization** — flat utility lists aren't supported
3. **Rigid lifecycle enum** — only 3 states, real systems have more
4. **Web-first bias** — top-level `cssVariable` and `properties` shortcuts
5. **Specific tier terminology** — `isPrimitive`/`isComponent` assumes a particular taxonomy

Additionally, several capabilities needed for real-world adoption are missing entirely.

## Goals

- Any design system can adopt these schemas without fighting the structure
- Multi-platform, multi-brand, multi-condition systems are first-class
- The language server gets richer signals for diagnostics and IntelliSense
- Backwards-compatible where feasible (v0.2 manifests should validate or migrate easily)

## Non-Goals

- **Not a token authoring format.** This is a *resolved output* schema for language servers and tooling — not a replacement for DTCG, Style Dictionary config, or Tokens Studio source files.
- **Not a build tool.** We describe what tokens/utilities look like after build, not how to transform them.
- **Not a component API schema.** CEM handles component definitions; we only extend it with lifecycle metadata.
- **Not prescribing naming conventions.** Systems can use any naming (BEM, Tailwind, custom) — the schema is convention-agnostic.
- **Not covering runtime behavior.** How tokens are applied (CSS custom properties, theme providers, runtime switching) is out of scope.

## Prior Art & Ecosystem Positioning

| Spec / Tool | Relationship to this schema |
|---|---|
| [W3C Design Tokens Community Group (DTCG)](https://tr.designtokens.org/format/) | DTCG defines a **source/authoring** format. We define a **resolved output** format. A build tool reads DTCG → outputs a Design Lasagna manifest. We align on type names where possible. |
| [Style Dictionary](https://amzn.github.io/style-dictionary/) | Style Dictionary transforms tokens into platform outputs. Our schema describes the *shape* of those outputs for consumption by language servers. A Style Dictionary custom format could emit our manifest. |
| [Figma Variables API](https://www.figma.com/developers/api#variables) | Figma's model uses collections, modes, and scoping. Our `conditions` (B2) and `collections` (B10) map to these concepts. |
| [Tokens Studio](https://tokens.studio/) | Tokens Studio is an authoring tool with its own JSON format. Like DTCG, it's upstream — our schema is downstream/resolved. |
| [Custom Elements Manifest (CEM)](https://github.com/webcomponents/custom-elements-manifest) | We extend CEM, not replace it. Our `cem-extensions.json` adds fields alongside standard CEM declarations. |
| [Tailwind CSS config](https://tailwindcss.com/docs/configuration) | Tailwind's config is a build input. Our utilities schema could describe the resolved utility classes that Tailwind produces. |

**Key positioning:** Design Lasagna schemas sit at the **resolved output** layer — between build tools (upstream) and developer tooling like language servers, linters, and documentation generators (downstream).

```
┌─────────────┐     ┌──────────────┐     ┌────────────────────────┐
│ Source/Auth  │────▶│  Build Tool  │────▶│  DL Manifest (this)    │

│ Tokens Studio│     │ custom       │     │  utilities.json        │

                                    ┌─────────────────┼─────────────────┐
                                    ▼                  ▼                  ▼
                              ┌──────────┐     ┌────────────┐     ┌──────────┐

                              │  IDE     │     │   Site     │     │  CI      │
                              └──────────┘     └────────────┘     └──────────┘
```

## Part A: Fixes to existing schema

### A1. Make `group` and `category` optional on tokens

**Problem:** Required fields force a specific organizational model.

**Change:** Remove `group` and `category` from the `required` array on `Token`. Add a note that systems using hierarchical organization should populate these.

```diff
- "required": ["id", "path", "group", "category", "resolved"],
+ "required": ["id", "resolved"],
```

**Rationale:** The `id` and `path` already encode hierarchy for systems that want it. Flat-token systems (e.g., Open Props, Tailwind's internal tokens) can skip group/category entirely.

**Migration:** Non-breaking — existing manifests still validate.

---

### A2. Make `path` optional

**Problem:** Some systems use flat token IDs (`color-primary`) without path segments.

**Change:** Remove `path` from required. When omitted, tooling derives path by splitting `id` on `.`.

```diff
- "required": ["id", "path", "group", "category", "resolved"],
+ "required": ["id", "resolved"],
```

**Migration:** Non-breaking.

---

### A3. Allow flat utility lists (alternative to categories)

**Problem:** Requiring `categories` forces categorization.

**Change:** Use `oneOf` at the root — either `categories` (grouped) or `utilities` (flat):

```json
{
  "oneOf": [
    {
      "required": ["schemaVersion", "categories"],
      "properties": { "categories": { ... } }
    },
    {
      "required": ["schemaVersion", "utilities"],
      "properties": { "utilities": { ... } }
    }
  ]
}
```

**Migration:** Non-breaking — existing manifests use `categories` and still validate.

---

### A4. Replace fixed `status` enum with extensible string + recommended values

**Problem:** `["draft", "ready", "deprecated"]` doesn't fit all lifecycle models.

**Change:**

```json
"status": {
  "type": "string",
  "description": "Component lifecycle status. Common values: 'draft', 'experimental', 'beta', 'rc', 'stable', 'deprecated', 'removed'. Any string is allowed to support custom lifecycle models.",
  "examples": ["draft", "experimental", "beta", "stable", "deprecated"]
}
```

**Rationale:** The language server can still key diagnostics off known values (`deprecated` → warning) while allowing systems their own terminology.

**Migration:** Breaking for strict consumers that relied on the enum. Language server should treat unknown statuses as informational.

---

### A5. Reframe web-shortcut fields as platform convenience

**Problem:** `cssVariable` and top-level `properties` privilege web.

**Change:** 
- Keep the fields (backwards compat) but mark as `"deprecated"` in v0.3 descriptions
- Add a note: "Prefer `platforms.web.reference` for new manifests"
- Long-term: remove in v1.0

```json
"cssVariable": {
  "type": ["string", "null"],
  "description": "DEPRECATED in v0.3 — use platforms.web.reference instead. CSS custom property name. Kept for backwards compatibility with web-only manifests."
}
```

**Migration:** Soft deprecation — existing manifests still validate, generators can migrate at their pace.

---

### A6. Replace `visibility` booleans with a `tier` string

**Problem:** `isPrimitive`/`isComponent` encodes one specific taxonomy.

**Change:**

```json
"tier": {
  "type": "string",
  "description": "Token tier in the system's hierarchy. Common values: 'primitive', 'semantic', 'component'. Any string allowed.",
  "examples": ["primitive", "semantic", "component", "global", "alias", "reference", "contextual"]
}
```

Remove `visibility` object (or keep as deprecated alias in v0.3).

**Migration:** Minor breaking — `visibility` users need to migrate to `tier`.

---

### A7. Make `counts` freeform

**Problem:** `counts.byGroup` / `counts.byCategory` couples stats to hierarchy.

**Change:**

```json
"counts": {
  "type": "object",
  "properties": {
    "total": { "type": "integer" },
    "by": {
      "type": "object",
      "description": "Token counts by any grouping dimension",
      "additionalProperties": {
        "type": "object",
        "additionalProperties": { "type": "integer" }
      }
    }
  }
}
```

Example:
```json
"counts": {
  "total": 340,
  "by": {
    "group": { "color": 120, "spacing": 45 },
    "tier": { "primitive": 80, "semantic": 200, "component": 60 },
    "platform": { "web": 340, "ios": 280 }
  }
}
```

## Part B: New capabilities

### B1. Design system manifest metadata

**Problem:** Manifests are anonymous — no identity, no version, no docs link.

**Change:** Add optional top-level `designSystem` object to both token and utility schemas:

```json
"designSystem": {
  "type": "object",
  "description": "Identity of the design system that produced this manifest.",
  "properties": {
    "name": {
      "type": "string",
      "description": "Human-readable design system name"
    },
    "version": {
      "type": "string",
      "description": "Design system version (semver)"
    },
    "documentation": {
      "type": "string",
      "format": "uri",
      "description": "URL to design system documentation"
    },
    "package": {
      "type": "string",
      "description": "Package identifier (e.g. npm package name)"
    }
  }
}
```

**Language Server benefit:** Can display "Token from Acme DS v3.2" in hover info.

---

### B2. Global modes/conditions declaration

**Problem:** Available modes are implicit — discovered by scanning all tokens.

**Change:** Add top-level `conditions` object to token schema:

```json
"conditions": {
  "type": "object",
  "description": "Declares the condition dimensions and their possible values for this system.",
  "additionalProperties": {
    "type": "object",
    "required": ["values"],
    "properties": {
      "description": { "type": "string" },
      "type": {
        "type": "string",
        "description": "Condition type — helps tooling understand which conditions are mutually exclusive. Common values: 'colorScheme', 'viewport', 'motion', 'contrast', 'density', 'brand'. Any string allowed.",
        "examples": ["colorScheme", "viewport", "motion", "contrast", "density", "brand"]
      },
      "values": {
        "type": "array",
        "items": { "type": "string" }
      },
      "default": {
        "type": "string",
        "description": "The default/fallback value"
      }
    }
  }
}
```

Example:
```json
"conditions": {
  "colorScheme": {
    "type": "colorScheme",
    "values": ["light", "dark", "high-contrast"],
    "default": "light"
  },
  "density": {
    "type": "density",
    "values": ["comfortable", "compact"],
    "default": "comfortable"
  },
  "brand": {
    "type": "brand",
    "description": "White-label brand variants",
    "values": ["main", "partner-a", "partner-b"],
    "default": "main"
  }
}
```

**Language Server benefit:** Can validate that `resolved`/`modes` keys match declared conditions, offer completions for mode values.

---

### B2b. Granular `type` values for preview rendering

**Problem:** The current `type` field is `["string", "null"]` with no guidance. The DTCG-aligned value `"dimension"` covers border-radius, border-width, spacing, sizes, font-sizes, and line-heights — all of which need different visual previews. Docs tools are forced to sniff `group + category + path` with brittle heuristics to pick the right renderer (see `getDimensionKind()` and `getTypographyKind()` in the Acme tokens-viewer).

**Change:** Keep `type` as a free string (not an enum) but document recommended values. Build tools SHOULD emit the most specific type possible. Docs tools fall back to heuristics only when the generic `"dimension"` is used.

```json
"type": {
  "type": ["string", "null"],
  "description": "Token type. Use the most specific value possible to enable docs tools to render appropriate previews without heuristics. Aligns with DTCG where applicable, extends with finer-grained dimension subtypes.",
  "examples": [
    "color",
    "dimension",
    "spacing",
    "size",
    "borderRadius",
    "borderWidth",
    "fontSize",
    "lineHeight",
    "letterSpacing",
    "fontFamily",
    "fontWeight",
    "duration",
    "cubicBezier",
    "opacity",
    "number",
    "shadow",
    "border",
    "gradient",
    "typography",
    "transition"
  ]
}
```

**Recommended type hierarchy:**

| Type | Preview rendering | DTCG equivalent |
|------|------------------|-----------------|
| `color` | Swatch (32×32, border-radius) | `color` |
| `spacing` | Vertical/horizontal bar | `dimension` |
| `size` | Square box (width=height) | `dimension` |
| `borderRadius` | Rounded corner preview | `dimension` |
| `borderWidth` | Border thickness preview | `dimension` |
| `fontSize` | "Aa" text sample at that size | `dimension` |
| `lineHeight` | Multi-line paragraph | `dimension`/`number` |
| `letterSpacing` | Spaced text sample | `dimension` |
| `fontFamily` | "The quick brown fox" in that font | `fontFamily` |
| `fontWeight` | Sample text at that weight | `fontWeight` |
| `duration` | Numeric display (maybe animation) | `duration` |
| `cubicBezier` | Easing curve visualization | `cubicBezier` |
| `opacity` | Opacity swatch overlay | `number` |
| `shadow` | Element with shadow applied | `shadow` |
| `border` | Element with border applied | `border` |
| `gradient` | Gradient bar | `gradient` |
| `typography` | Full text sample (composite) | `typography` |
| `dimension` | Generic bar (fallback) | `dimension` |
| `number` | Numeric display | `number` |

**Rule:** If a build tool can only emit DTCG types, `"dimension"` is valid — docs tools fall back to `group + category` heuristics. But specific types eliminate all guesswork.

**Language Server benefit:** Can offer type-specific autocomplete for `resolved` values (e.g., suggest hex colors for `type: "color"`, suggest px/rem for `type: "spacing"`).

### B3. Structured `resolved` values for composite tokens

**Problem:** No guidance for composite token values (typography, border, shadow).

**Change:** Add `valueSchema` hint to Token, and define well-known composite shapes:

```json
"resolved": {
  "type": "object",
  "description": "Resolved values per condition. Values may be primitives (string, number) or composite objects for multi-value tokens.",
  "additionalProperties": {
    "oneOf": [
      { "type": "string" },
      { "type": "number" },
      { "$ref": "#/definitions/CompositeValue" }
    ]
  }
}
```

```json
"CompositeValue": {
  "type": "object",
  "description": "Structured value for composite tokens (typography, border, shadow, etc.)",
  "additionalProperties": true,
  "examples": [
    {
      "fontFamily": "Inter",
      "fontSize": "32px",
      "fontWeight": 700,
      "lineHeight": 1.2,
      "letterSpacing": "-0.02em"
    },
    {
      "width": "1px",
      "style": "solid",
      "color": "#e0e0e0"
    }
  ]
}
```

### B4. Token `since` field

**Problem:** No way to know when a token was introduced.

**Change:** Add optional `since` to Token:

```json
"since": {
  "type": "string",
  "description": "Version or date when this token was introduced. Helps tooling warn about minimum version requirements.",
  "examples": ["2.0.0", "2025-01-15", "Q1-2025"]
}
```

### B5. Utility exclusivity groups

**Problem:** No way to declare utilities that conflict with each other.

**Change:** Add `exclusiveGroup` to UtilityClass:

```json
"exclusiveGroup": {
  "type": "string",
  "description": "Utilities sharing the same exclusiveGroup are mutually exclusive — applying more than one is a diagnostic warning."
}
```

Example:
```json
{ "name": "text-heading-1", "exclusiveGroup": "text-style" },
{ "name": "text-heading-2", "exclusiveGroup": "text-style" },
{ "name": "text-body-1", "exclusiveGroup": "text-style" }
```

**Language Server benefit:** Flags conflicting utilities applied to the same element.

### B6. Utility variants (states & responsive)

**Problem:** No way to express hover/focus/responsive variants.

**Change:** Two-level design — declare variant *patterns* at the manifest level, then utilities opt in.

**Manifest-level declaration** (what variant patterns exist system-wide):

```json
"variantPatterns": {
  "type": "object",
  "description": "System-wide variant patterns. Utilities opt in rather than repeating the pattern.",
  "properties": {
    "states": {
      "type": "object",
      "description": "Available pseudo-state variants. Keys are state names.",
      "additionalProperties": {
        "type": "object",
        "properties": {
          "format": {
            "type": "string",
            "description": "Pattern for generating variant names. Use {utility} as placeholder.",
            "examples": ["hover:{utility}", "{utility}--hover", "{utility}:hover"]
          },
          "description": { "type": "string" }
        }
      }
    },
    "responsive": {
      "type": "object",
      "description": "Responsive breakpoint variants.",
      "properties": {
        "breakpoints": {
          "type": "array",
          "items": { "type": "string" },
          "description": "Available breakpoint names",
          "examples": [["sm", "md", "lg", "xl"]]
        },
        "format": {
          "type": "string",
          "description": "Pattern for generating responsive variants",
          "examples": ["{breakpoint}:{utility}", "{utility}-{breakpoint}"]
        }
      }
    }
  }
}
```

**Utility-level opt-in** (lightweight booleans or override):

```json
"variants": {
  "type": "object",
  "properties": {
    "states": {
      "oneOf": [
        { "type": "boolean", "description": "true = supports all declared state variants" },
        { "type": "array", "items": { "type": "string" }, "description": "Subset of state names this utility supports" }
      ]
    },
    "responsive": {
      "type": "boolean",
      "description": "Whether this utility supports responsive breakpoint variants"
    }
  }
}
```

Example:
```json
{
  "variantPatterns": {
    "states": {
      "hover": { "format": "hover:{utility}", "description": "Applies on pointer hover" },
      "focus": { "format": "focus:{utility}", "description": "Applies on keyboard focus" },
      "active": { "format": "active:{utility}", "description": "Applies while pressed" }
    },
    "responsive": {
      "breakpoints": ["sm", "md", "lg", "xl"],
      "format": "{breakpoint}:{utility}"
    }
  },
  "utilities": [
    { "name": "bg-primary", "variants": { "states": true, "responsive": true } },
    { "name": "sr-only", "variants": { "states": false, "responsive": false } },
    { "name": "text-heading-1", "variants": { "states": ["hover", "focus"], "responsive": true } }
  ]
}
```

**Why not per-utility variant strings?**  
A system with 500 utilities × 3 states = 1500 variant name strings. With format patterns declared once, utilities just say `true`/`false`. The LSP generates the variant names from the pattern.

### B7. Token relationships

**Problem:** No way to express semantic connections between tokens.

**Change:** Top-level `tokenRelations` array — avoids bidirectional duplication.

```json
"tokenRelations": {
  "type": "array",
  "description": "Semantic relationships between tokens. Declared once, tooling infers both directions.",
  "items": {
    "type": "object",
    "required": ["type", "tokens"],
    "properties": {
      "type": {
        "type": "string",
        "description": "Relationship type",
        "examples": ["contrastPair", "scale", "stateSet", "complementary"]
      },
      "tokens": {
        "type": "array",
        "items": { "type": "string" },
        "description": "Token IDs in this relationship (order may be significant for some types)"
      },
      "description": {
        "type": "string"
      }
    }
  }
}
```

Example:
```json
"tokenRelations": [
  {
    "type": "contrastPair",
    "tokens": ["color.bg.primary", "color.text.on-primary"],
    "description": "Background and its foreground text color"
  },
  {
    "type": "scale",
    "tokens": ["spacing.1", "spacing.2", "spacing.3", "spacing.4", "spacing.5"]
  },
  {
    "type": "stateSet",
    "tokens": ["color.bg.interactive", "color.bg.interactive-hover", "color.bg.interactive-pressed"]
  }
]
```

**Why not `relations` on each token?**  
- A contrast pair declared on both sides is redundant and can drift.
- A 10-step spacing scale would need each token to list 9 neighbors.
- State sets (default/hover/pressed/disabled) would repeat across all members.

Top-level declaration is DRY and makes relationships first-class entities the LSP can index once.

**Language Server benefit:** "You used `color.bg.primary` — the recommended text color is `color.text.on-primary`." Also: "You used `color.bg.interactive` — related states: hover, pressed."

          "type": "array",

        "category": { "type": "string" },

          "type": "array",

          "type": "array",
          "items": { "type": "string" },

          "type": "object",

### B10. Token collections

**Problem:** Figma and other tools group tokens into collections that share mode dimensions. A flat token array doesn't capture which tokens share the same condition axis.

**Change:** Two-part design — collections are *declared* at the top level (with optional defaults), and tokens *reference* their collection.

**Top-level declaration** (what collections exist, their condition axes, and shared defaults):

```json
"collections": {
  "type": "object",
  "description": "Named token collections. Keys are collection identifiers.",
  "additionalProperties": {
    "type": "object",
    "properties": {
      "name": {
        "type": "string",
        "description": "Human-readable collection name (e.g. 'Semantic colors')"
      },
      "description": { "type": "string" },
      "conditions": {
        "type": "array",
        "items": { "type": "string" },
        "description": "Which condition dimensions apply to tokens in this collection (references keys from top-level 'conditions')"
      },
      "defaults": {
        "type": "object",
        "description": "Default values inherited by all tokens in this collection (tokens can override).",
        "properties": {
          "tier": { "type": "string" },
          "priority": { "type": "integer", "minimum": 0, "maximum": 100 },
          "usage": { "$ref": "#/definitions/Usage" },
          "format": { "$ref": "#/definitions/Format" }
        }
      }
    }
  }
}
```

**Token-level reference** (lightweight — just a string):

```json
"collection": {
  "type": "string",
  "description": "Collection this token belongs to (references a key in top-level 'collections')"
}
```

Example:
```json
{
  "collections": {
    "semantic-bg": {
      "name": "Semantic background colors",
      "conditions": ["colorScheme", "brand"],
      "defaults": {
        "tier": "semantic",
        "priority": 70,
        "usage": { "context": "background", "allowedProperties": ["background-color", "background"] },
        "format": { "colorSpace": "srgb" }
      }
    },
    "primitives": {
      "name": "Primitive color palette",
      "conditions": ["colorScheme"],
      "defaults": {
        "tier": "primitive",
        "priority": 20
      }
    },
    "spacing": {
      "name": "Spacing scale",
      "conditions": ["density"],
      "defaults": {
        "tier": "semantic",
        "priority": 60,
        "format": { "unit": "rem" }
      }
    }
  },
  "tokens": [
    {
      "id": "color.bg.primary",
      "collection": "semantic-bg",
      "resolved": { "light/main": "#ffffff", "dark/main": "#1a1a1a" }
    },
    {
      "id": "color.bg.primary-hover",
      "collection": "semantic-bg",
      "priority": 40,
      "resolved": { "light/main": "#f5f5f5", "dark/main": "#2a2a2a" }
    }
  ]
}
```

**Why collection-level defaults?**  
Without them, 200 background tokens each repeat `"tier": "semantic", "priority": 70, "usage": { "context": "background", ... }`. With defaults, tokens only declare what's different — the hover variant overrides `priority: 40` because it's less commonly used.

**Inheritance rule:** Token-level fields override collection defaults. Omitted fields inherit. This mirrors CSS cascade logic that DS developers already understand.

**Why not `tokenIds` on the collection?**  
A collection with 300 color tokens would need a 300-item ID array — redundant, hard to maintain, guaranteed to drift. Putting the reference on the token (one string per token) is DRY, easy to generate, and mirrors how Figma's internal model works (variables belong to a collection, not the other way around).

**Language Server benefit:** Knows which conditions are valid for a given token's `resolved` keys. Can warn: "Token `color.bg.primary` is in collection `semantic-bg` which supports `colorScheme` and `brand` — but resolved key `compact` doesn't match any declared condition value."

### B11. Accessibility metadata

**Problem:** Design systems are responsible for ensuring accessible contrast, touch targets, and motion safety. The schema has no way to express accessibility properties.

**Change:** Add optional `a11y` object to Token, with per-condition contrast support:

```json
"a11y": {
  "type": "object",
  "description": "Accessibility metadata for this token.",
  "properties": {
    "wcagContrast": {
      "oneOf": [
        { "$ref": "#/definitions/ContrastInfo" },
        {
          "type": "object",
          "description": "Per-condition contrast info (contrast can differ by mode).",
          "additionalProperties": { "$ref": "#/definitions/ContrastInfo" }
        }
      ]
    },
    "minTargetSize": {
      "type": "string",
      "description": "Minimum touch/click target size (for spacing/sizing tokens used on interactive elements)",
      "examples": ["44px", "24px"]
    },
    "motionSafe": {
      "type": "boolean",
      "description": "Whether this token's value respects prefers-reduced-motion (for duration/easing tokens)"
    }
  }
}
```

```json
"ContrastInfo": {
  "type": "object",
  "properties": {
    "ratio": { "type": "number", "description": "Contrast ratio (e.g. 4.52)" },
    "against": { "type": "string", "description": "Token ID this was measured against" },
    "level": { "type": "string", "examples": ["AA", "AAA", "AA-large", "fail"] }
  }
}
```

Example (simple — same across modes):
```json
"a11y": { "wcagContrast": { "ratio": 7.1, "against": "color.bg.primary", "level": "AAA" } }
```

Example (per-condition — differs by mode):
```json
"a11y": {
  "wcagContrast": {
    "light": { "ratio": 7.1, "against": "color.bg.primary", "level": "AAA" },
    "dark": { "ratio": 4.6, "against": "color.bg.primary", "level": "AA" }
  }
}
```

**Note:** `a11y` can also be set in collection `defaults` — e.g., all tokens in a "text colors" collection could inherit `"against": "color.bg.primary"` and only need per-token `ratio`/`level`.

**Language Server benefit:** Warnings like "This color pair achieves 3.1:1 in dark mode — fails WCAG AA for normal text."

### B12. Documentation links

**Problem:** No way to link a token/utility/component to external documentation (Storybook, Figma, guidelines).

**Change:** Two levels — URL *templates* at the manifest level (DRY), and per-item *overrides* for exceptions.

**Manifest-level templates** (in `designSystem`):

```json
"designSystem": {
  "properties": {
    "docsTemplates": {
      "type": "object",
      "description": "URL templates for generating documentation links. Use {id} for token/utility ID, {name} for name, {group} for group, or any token field in braces.",
      "properties": {
        "url": { "type": "string", "examples": ["https://ds.example.com/tokens/{id}"] },
        "figma": { "type": "string", "examples": ["https://figma.com/file/abc123?node-id={metadata.figmaNodeId}"] },
        "storybook": { "type": "string", "examples": ["https://storybook.example.com/?path=/docs/{group}--{id}"] }
      },
      "additionalProperties": { "type": "string" }
    }
  }
}
```

**Per-item override** (only when template doesn't work):

```json
"docs": {
  "type": "object",
  "description": "Documentation links for this item. Overrides manifest-level templates.",
  "properties": {
    "url": { "type": "string", "format": "uri" },
    "figma": { "type": "string", "format": "uri" },
    "storybook": { "type": "string", "format": "uri" }
  },
  "additionalProperties": { "type": "string", "format": "uri" }
}
```

Example:
```json
{
  "designSystem": {
    "name": "Acme DS",
    "docsTemplates": {
      "url": "https://design.acme.com/tokens/{id}",
      "figma": "https://figma.com/file/Xk2j/{metadata.figmaNodeId}"
    }
  },
  "tokens": [
    {
      "id": "color.bg.primary",
      "metadata": { "figmaNodeId": "100:200" },
      "resolved": { "light": "#ffffff" }
    },
    {
      "id": "color.bg.legacy-brand",
      "resolved": { "light": "#003366" },
      "docs": { "url": "https://wiki.acme.com/legacy/brand-colors" }
    }
  ]
}
```

**Why templates?**  
A system with 500 tokens where each has a predictable docs URL shouldn't need 500 `"docs": { "url": "..." }` objects. One template handles 95% of cases; per-item `docs` handles exceptions.

**Language Server benefit:** "Open in Figma" / "View docs" quick actions in hover panels — works for every token without per-token config.

### B13. Usage constraints / scoping

**Problem:** Some tokens should only be used in specific contexts (e.g., background colors shouldn't be applied to text). No way to express this.

**Change:** Add optional `usage` object to Token:

```json
"usage": {
  "type": "object",
  "description": "Constraints on how this token should be used.",
  "properties": {
    "allowedProperties": {
      "type": "array",
      "items": { "type": "string" },
      "description": "CSS properties (or platform equivalents) this token is intended for.",
      "examples": [["background-color", "background"], ["color"], ["border-color", "outline-color"]]
    },
    "context": {
      "type": "string",
      "description": "Semantic usage context",
      "examples": ["background", "text", "border", "interactive", "surface", "overlay"]
    },
    "doNot": {
      "type": "array",
      "items": { "type": "string" },
      "description": "Explicit misuse warnings",
      "examples": [["Do not use for text color", "Do not use on non-interactive elements"]]
    }
  }
}
```

**Language Server benefit:** Diagnostic when `color.bg.primary` is used in a `color:` property. Suggestions scoped to context.

---

### B14. Autocomplete priority / sort weight

**Problem:** Some tokens are used far more than others. In a list of 400 tokens, `color.bg.primary` should rank above `color.bg.surface-raised-hover-alt`.

**Change:** Add optional `priority` to Token and UtilityClass:

```json
"priority": {
  "type": "integer",
  "minimum": 0,
  "maximum": 100,
  "description": "Sort weight for autocomplete (0 = lowest, 100 = highest). Defaults to 50 when omitted. Commonly-used tokens should have higher priority."
}
```

**Language Server benefit:** Better autocomplete ordering. Can also be combined with usage analytics.

---

### B15. Manifest composition (multi-file)

**Problem:** Large design systems split tokens across multiple files (primitives, semantic, component-specific). No way to declare how manifests compose.

**Change:** Add optional `extends` to the token manifest root:

```json
"extends": {
  "type": "array",
  "items": {
    "type": "string",
    "description": "Path or URL to another manifest this one extends/depends on"
  },
  "description": "Other manifests that should be loaded alongside this one. Useful for systems that split tokens across files (e.g. primitives.json + semantic.json + component-tokens.json)."
}
```

Example:
```json
{
  "schemaVersion": "0.3.0",
  "extends": [
    "./primitives.json",
    "./semantic.json"
  ],
  "tokens": [
    { "id": "button.bg.primary", "resolved": { "light": "{color.bg.interactive}" } }
  ]
}
```

**Language Server benefit:** Automatically discovers and loads related manifests. Resolves cross-file alias references.

## Part B-AI: Agent-oriented capabilities

These additions specifically help AI coding agents (Copilot, Cursor, Claude, custom agents) make better decisions when generating, migrating, or validating design system code.

### B16. Semantic search hints / synonyms

**Problem:** An AI agent gets the prompt "I need a blue button background." The correct token is `color.bg.interactive` — but there's nothing connecting "blue", "button", or "CTA" to that token ID.

**Change:** Add optional `keywords` to Token and UtilityClass:

```json
"keywords": {
  "type": "array",
  "items": { "type": "string" },
  "description": "Natural-language synonyms and search terms. Helps AI agents and fuzzy search match human intent to the correct token. Include: common names, use cases, visual descriptions, component associations."
}
```

Example:
```json
{
  "id": "color.bg.interactive",
  "description": "Background for primary interactive elements (buttons, links).",
  "keywords": ["button", "action", "CTA", "primary", "clickable", "blue", "brand"]
}
```

```json
{
  "id": "spacing.4",
  "description": "Base spacing unit (16px). Used for component padding and gaps.",
  "keywords": ["padding", "gap", "margin", "medium", "base", "16"]
}
```

**Agent benefit:** RAG/embedding search, fuzzy autocomplete, and intent-to-token mapping all improve dramatically. The AI can match "add some padding to the card" → `spacing.4` even though "padding" isn't in the ID.

## Part C: Shared definitions

Several definitions are duplicated across schemas. v0.3 should extract shared types:

- `Deprecated` — identical in tokens + utilities + icons
- `DesignSystemMeta` — new, shared across all manifests
- `PlatformMapping` — similar concepts in tokens + utilities + icons
- `Docs` — documentation links (B12), shared across all entity types
- `Since` — version/date introduced, shared across all entity types

**Recommendation:** Keep schemas seacme-contained (inline shared definitions in each schema) for simpler consumption. Document the canonical shapes in a `DEFINITIONS.md` reference to keep them in sync across schemas. Tooling should not require resolving cross-file `$ref`.

These scenarios demonstrate that the schema is not biased toward any single system's architecture.

### Scenario 1: Tailwind-style utility-first system

  "designSystem": { "name": "WindUI", "version": "4.0.0" },
  "variantPatterns": {

      "hover": { "format": "hover:{utility}" },
      "focus": { "format": "focus:{utility}" },
      "active": { "format": "active:{utility}" }
    },
    "responsive": {
      "breakpoints": ["sm", "md", "lg", "xl", "2xl"],
      "format": "{breakpoint}:{utility}"
    }
  },
  "utilities": [
    {
      "name": "bg-blue-500",
      "exclusiveGroup": "background-color",
      "priority": 70,
      "variants": { "states": true, "responsive": true },
      "platforms": {
        "web": { "className": "bg-blue-500", "properties": { "background-color": "#3b82f6" } }

## Open questions

1. **Should `conditions` replace `modes` on individual tokens?** Or should `modes` keys reference declared conditions? Proposal: `resolved` keys use a `condition/value` composite key format (e.g., `"light/main"`), and `modes` is deprecated in favor of a clearer name.
2. **Should we support JSON Schema `$ref` across files** (common.json) or keep schemas seacme-contained? Seacme-contained is simpler for consumers but means duplication.
3. **Is the icons manifest in scope for v0.3** or should it be a separate RFC?
4. **Should `tier` support multiple values?** (A token could arguably be both "semantic" and "component-scoped".) Proposal: single string — use `tags` for additional classification.
5. **How should `extends` (B15) interact with `collections` (B10)?** Can a collection reference tokens from an extended manifest?
6. **Should `a11y.wcagContrast` be per-mode?** A color pair might pass in light mode but fail in dark mode.
7. **Should `usage.allowedProperties` be platform-specific?** Web uses CSS properties, iOS uses SwiftUI modifiers. Proposal: keep it under `platforms` or use generic context strings.
8. **How do condition combinations work in `resolved` keys?** Is it `"light/main"` (slash-separated), nested objects, or something else?
9. **Should there be a `maxPriority` or normalization rule?** Or is 0–100 sufficient guidance without enforcement?
